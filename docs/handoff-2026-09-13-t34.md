## 1. 这一票的三条硬事实(改这个适配器之前先读)

1. **提交响应的 `data` 是数组**:`{"code":200,"data":[{"status":"submitted","task_id":"task_…"}]}`
   —— 第一版按对象取,**白花了一次生成**(¥0.4375);
2. **轮询响应的 `data` 是对象**:`{id, task_id, status, progress, estimated_time, cost, credits_cost}`;
   完成时 `result.music[i].audio_url`(**一条请求给两个变体**,我们取第一个;
   `image_url` 也是 http 链接但**不是音频**);
3. **中间态是 `processing`**(带 `progress`%);终态 `completed`;计费 `credits_cost: 0.5` /
   `usage.amount: 0.4375 元`。

## 2. `collect`:这一票真正值钱的那半

一次真生成是**真金**。而"上游已经生成了、但我们没拿到"有几种现实原因(认不出响应形状、
下载口没装配、进程被杀)。所以:

- 异步制提交拿到的**上游任务 id 记进账本**(`AudioTask.upstreamTaskId`),失败原因里也带一句;
- 新增 `galfree_audio_queue(action:"collect", task_id, upstream_task_id)`:
  **不重新提交**、只按 id 问一次状态 → 成了就下载 + 经网关落盘 → `awaiting-review`;
  还在跑就如实说"还在跑"(**不改账本**,不写一笔"没变化");
- 取回来之后会删掉上次那条"没拿到"的失败原因(留着就是过期的话)。

## 5.1 一次**未解**的报错 + 因此补上的报告链(2026-09-13 深夜)

**事情**:经 T33 入口出的第一首 BGM 落盘、接进 `sc01_classroom` 之后,我跑了一次
「从这一场开始」的试玩:窗口开了、**用户看到错误页**、进程以 **退出码 1** 自己退出(165 秒),
而插件报的是 `traceback: null`。随后用户自己再跑一次(从头)⇒ **技术通过**(退出码 0、25 秒)。
**那次报错到底是什么,至今不知道** —— 没截到图、也没留下文件。

**为什么没留下证据(两个原因,都已修)**:
1. Ren'Py 的**错误页把 traceback 写进运行目录的文件**(`traceback.txt`)、**不写 stdout**,
   而插件只从进程日志里找 traceback ⇒ 只剩一句"看退出码";
2. `from:` 试玩跑在**临时副本**里,跑完 `finally` 就把副本删了 ⇒ 那份文件被销毁。
   真机复现还排除了"音乐那行"的嫌疑:`play music` 在第一句台词**之前**执行,而我的复现
   跑到第一句都没报错(用 `label splashscreen: jump …` 绕过主菜单,不靠人点)。

**修法**(`src/service/playtest.ts`):`realSpawn` 在进程退出后、副本被删之前读一次
`<运行目录>/traceback.txt`(`readRunTraceback`),**只认比本次启动新的那一份**
(旧文件会被当成本次结果 —— 那种假事实比"没有"更坏),读到了就并进日志 ⇒ 下次同样的
错误会带着原文回来。守卫在 `playtest.test.ts` 四条(新文件认得出 / 旧文件不认 / 缺失为空 / 超长截断)。

**还欠的一条**:`from:` 试玩要人**点「开始游戏」**才进那场戏(副本只覆写 `start`),
所以"窗口开了没跑起来"与"跑起来了"在报告里分不出来 —— 只有人能说。这不是缺陷,
但排障时要知道。顺带:那场戏因为加了 `play music` 一行,**审读戳失效转「待复审」**(
内容变了 —— 这是设计,不是 bug;等复看后由人重盖)。
