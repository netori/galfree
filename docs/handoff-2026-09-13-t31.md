## 2. 本轮**踩过并已修**的坑(这几条最值钱)

1. **`tint` / `shade` 是线性 RGB 插值,不是 HLS**。`renpy/color.py` 里 `_interpolate_tuple`
   看着像 HLS,而 `Color('#ff0000').tint(.5)` 实测是 `#ff7f7f`(HLS 那条路给 `#df9f9f`)。
   我照 docstring 写了第一版,颜色"看起来也挺合理",只有拿引擎的值对才发现。
2. **`replace_hsv_saturation` → `replace_value` 的中间值必须留在浮点里**。引擎的 `Color`
   自己缓存 hsv;若中途"转成 RGB 字节再转回来",饱和度会从 `.25` 变成 `.2396`
   —— 颜色差一个色阶(`#2f3f3f` vs 引擎的 `#2f3e3f`)。
3. **读 `.hsv` 时分量 round 到 8 位小数**。不照做就差一格(`#ff7ead` vs `#ff7fae`)。
   同理 `insensitive` 的 alpha 实测是 `7f`(127)不是 `80`。
4. **staging 里必须先删掉旧的一套界面图**。引擎只**覆盖**它画的那几十张,不删旧的一套里
   多出来的(手机版那种只在小屏变体下生成的图)—— 不清的话,收产物会把**旧主题的图**
   当成"这次的产物"写回项目。
5. **写完 `gui.rpy` 要保住原来的换行符**。Windows 上 SDK 写出来的是 CRLF;只按 `\n` 切再拼
   会把被改的那几行变成 LF —— 一份文件里混两种换行(实测 481 个 CRLF 变 469 个)。
6. **`generate_gui --replace-code` 会把项目自己的 `gui.rpy` 换掉**(它把 `--template` 的
   `gui.rpy` 拷过去),所以要动的是**颜色 define 那 13 行**,不是整个文件。
   `gui.hover_color` 在模板里是**表达式**(`Color(gui.accent_color).tint(.6)`)——
   同一份文件里既有"表达式"又有"陈旧字面量"(`gui.muted_color`),钉成字面量才自洽。
7. 写 define 的**引号是单引号**:引擎的 `update_defines` 用 `repr(hexcode)`,两边逐字一致
   (实测 12 行完全相同),于是"引擎再跑一次"也不会把文件改成另一种写法。

## 3. 三个必须知道的引擎事实(都实测过)

| 事实 | 判据 |

## 4.5 音乐与语音**拆成两条渠道**(2026-09-13 下半场,发起人指出)

**起因**:发起人看到现状后说「音乐和 TTS 要分开」。查下来他指的是一件**与 ADR 不符**的事 ——
ADR-0012 的原话是"**三条线 = 图像 / 音乐 / 语音。每条线一个独立渠道**(独立端点 + 密钥 +
模型目录),因为它们的上游与协议不重叠",而 T27 当初把音乐与语音做成了**共用一条**
(四个设置键 `audioBaseUrl` 一族)。

**改了什么**:

| 层 | 从 | 到 |
|---|---|---|
| 设置 | `audioBaseUrl` 一族 4 个键 | `music*` / `voice*` **各 4 个键**(两段界面) |
| 错误码 | `no-audio-channel` | `no-music-channel` / `no-voice-channel`(按用途分,说清该去配哪一段) |
| 拼渠道 | 一条 | `audioChannelFromSettings(settings, purpose)` —— 同一个函数调两次,**按用途过滤目录** |
| 跑任务 | 一条渠道 | 按 `task.purpose` 查渠道(两条目录不互相兜底) |
| 跑队列 | 全跑 | **`runAudioQueue(ref, {purpose})` 只跑那一类**(否则面板写"会发出 1 条"却替另一条渠道花钱) |
| 面板 | 一张「音频生成」卡 | **两张**(音乐 / 语音;语音那张带「语音批量清单」) |
| agent | 无音频渠道读入口 | `galfree_audio_channel`(两条一起报,建任务前先看) |

**没变的**:任务账本仍是**一份**(`.studio/audio-tasks.json`)—— ADR 要的是"渠道分开",
不是"任务也要两份";每条任务按自己的 `purpose` 找渠道。出网端口也仍是一份
(发一个 HTTP 请求没有两条;分两份反而会让"下载口只装配了一半"变成可能)。

**两条本轮学到的**:

1. **"共用一条渠道"是那种会悄悄发生的偏差**:它不报错、能跑通、看起来还更省事,
   代价要到人换上游那天才显形("我换了音乐那家,语音怎么也不出声了")。判据:**渠道这一层
   只该问"这条线自己的端点是什么"**,而不是"这几条线能不能凑一个端点"。
2. **"数得准"与"跑得准"必须是同一处判断**:第一版只在面板上把回执过滤了一遍,
   于是"排队数"按用途算、**真发出去的请求**却不按 —— 面板上的花费数字与事实不符。
   现在 purpose 一路传到接缝,在建队列那一步就分流(有守卫:音乐那一下不得让语音的任务变 `running`)。

**旧配置**:那四个旧键**不再被读取**、也**不自动迁移**(端点原本算音乐还是语音只有人知道);
设置文档里还留着它们时,设置面板会**如实提示一句**(schema 会剥掉未知键,不提示的话
人只会看到"我配的渠道没了")。ADR-0012 的落地修订里写明了这一条。

## 5. 慢带现在的处境(重要)

`npm run test:slow` 实测:**8 文件 44 通过 + 1 跳过 + 1 失败**。

那条失败是 `sdk.slow.test.ts` 的「从某场试玩:真 SDK 下入口真的落在该场景,且用户项目不被污染」,
报 `EPERM: unlink …\renpy-pinned\renpy.exe`。**已用 `git stash` 在干净的 HEAD 上复跑,同样红**
—— 不是 T31 带出来的。根因(已查明):

**这台机器上游戏窗口不会自己退出**,于是那一次试玩走满 3 分钟上限(`timedOut: true`),
回执之后子进程还没被完全回收,夹具清理时的 `unlink renpy.exe` 撞上 Windows 的文件锁。
用例里那两条真断言(`traceback.txt` 不在、用户项目没被污染)**都过了** —— 红的是 `afterEach` 的清理。

**值得单独开一张票**:要么清理那一步对"进程刚被杀、文件还锁着"有兜底(重试 + 宽限),
要么让那条用例自己主动关窗(而不是等它自己退)。**发版前不能就这么过去。**
